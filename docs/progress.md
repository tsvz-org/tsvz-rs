## Questions waiting for the user
- **Q4 (A1). On macOS, take `flock` as TSVZ.py does, and drop the lock-handle table?** After it: macOS takes `flock` (TSVZ.py 5.3 and later; it still excludes TSVZ.py 5.2's `lockf`, which TSVZ's macOS CI checked 2026-11-04); Linux is unchanged (open-file-description locks, on every targeted kernel); `tsvz::lock::Handle` goes, with the README's library paragraph that tells programs to open a store's files through it. It brings a **known limitation that needs your OK**: where neither lock exists (Linux before 3.15 without the backport, which is CentOS 7.0 to 7.4 and outside the targets, or a macOS network mount that refuses `flock`), the fallback classic lock can be lost for a moment by a multi-threaded `tsvz serve`, so a concurrent TSVZ.py writer could lose a record. Keeping costs about 350 code and 225 test lines, a process-wide table that delays file closes, a CI step, and four fixes so far. Options: **Switch, and accept the known limitation (Recommended)** / Keep as is. Waits on it: the prototype (-244 code, -269 test lines, Linux suite green; it needs a run on a Mac), the README's library paragraph, and the "flock on macOS" step of the deferred "Rust readers take no lock" entry. Your words it touches: none dropped; it completes an optional step of your 2026-11-04 pick "Deferred in tsvz-rs (Recommended)".
- **Q5 (A2). List a store's parts at every check, instead of trusting the directory's change time?** After it: answers are the same everywhere; a handler whose store directory has been quiet for 2 s makes 3 more directory listings per set/get pair (59.6 syscalls instead of 42.7, strace), about +3 us on a request of about 9 us (bench/RESULTS.md, 2026-10-16); tsvz-rs's handler stays about 3.5 times as fast as TSVZ.py's. Keeping costs about 350 code and 450 test lines, the longest silent-choices row, and a rule that needed five correctness patches (mergerfs, remounts, a symlinked part 0, whole-second change times, a clock stepped back), each a case where the handler would have answered from parts it no longer had. Options: **Always list (Recommended)** / Keep the trust. Waits on it: the prototype (-349 code, -448 test lines, green) and S7 (merging two statfs tables, worth building only if the trust is kept). Your words it touches: none.
- **Q6 (A3). Compress a whole handler batch at one member size, as TSVZ.py does?** After it: reads are unchanged; only a batch that itself sets `#_member_size_#` (or comes right after one still queued) keeps the size in force when it started, 1 MiB by default (§16.7 is a SHOULD). It happens only when a client changes the member size and writes in the same batch, such as while setting a store up. Keeping costs about 45 code and 110 test lines. Options: **One size per batch (Recommended)** / Keep. Waits on it: the member-size runs in write.rs and engine.rs. Your words it touches: none.
- **Q7 (A4). When a handler stops, close its socket as TSVZ.py does, instead of answering waiting clients "the handler is stopping"?** After it, for a command that reaches a handler as it stops (usually milliseconds, up to about 6 s while another client is mid-request): reads run on the files and succeed (today they exit 1, because the router falls back to the files only on a lost connection, which is a real bug this fixes); writes still exit 1, saying "may or may not have been applied" instead of "the handler is stopping", and nothing is applied either way. Keeping costs about 50 code and 80 test lines and five limits (128 clients, 1 s, 200 ms, 16 reads, 64 KiB). Options: **Close the socket as TSVZ.py does (Recommended)** / Keep the refusal. (Rerouting reads on the refusal's message would key on message text, against RULES principle 9, so it is not offered.) Waits on it: the refusal code in server.rs. Your words it touches: none.
- **Q8 (A6). Keep every copy of a damaged part that a scrub makes, as TSVZ.py does?** After it: only when a scrub of a damaged one-part store is retried because a writer appended in between, two `.damaged-<time>` copies stay instead of one, both named in the warnings. Keeping costs about 26 lines and one test. Options: **Keep every copy (Recommended)** / Keep the pruning. Waits on it: the backup pruning in maint.rs. Your words it touches: none.
