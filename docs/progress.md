The question as asked: **Q11 (0.2.1): a key typed with a trailing tab or line break names the cell that holds it, never the key without it?** (Written 2026-11-23 by the main session; chief may decide it.) The one rule built after 0.2.1's held release names every loose key as the reader names its cell: encode it, trim the encoded cell, decode. So `$'a\n'` names the row `a<LF>`, and in a tab file `$'b\t'` names `b<sep>`. What the operator sees, against 0.2.0: `get`, `has` and `pop` of `$'b\t'` on a file with only row `b` exit 3 (0.2.0 and TSVZ.py printed row `b`); a one-column `delete $'b\t'` removes nothing (0.2.0 removed `b`); a multi-column one appends a tombstone that deletes nothing (0.2.0 deleted row `b`); a trailing blank (`'a '`) is still trimmed, as before. For `$'a\n'`: 0.2.0 refused at more than one column and exited 3 for `get`; the build before this one deleted row `a`, the regression that held the release. TSVZ.py has no single rule here: its loose `get`, `has` and `pop` rstrip the key, its `delete` does not, and its one-column delete removes both `a` and `a<LF>`. Why the reader's rule: it never acts on a row the operator did not type, and a key that names no row fails visibly for `get`, `has` and `pop` (exit 3). Options: **(a) the reader's rule, as built, with one README line on keys typed with a trailing tab or line break (recommended)**; (b) rstrip a typed key before naming it, as TSVZ.py's `get` does: `$'b\t'` acts on `b` again, but `delete $'a\n'` then deletes row `a` at more than one column, the held regression; (c) the reader's rule, and a `delete` that names no row says so on standard error. What waits on it: 0.2.1's release. Your words it touches: the release gate (2026-11-09): with (a) a few typed keys that acted on a near row now miss it, and none acts on a wrong row.

The cost: `tsvz delete` (and `pop`, `popitem`) in a compressed loose file (`.tsv.gz` and the like) now reads the whole file into memory before it writes. On 4,000,000 rows (228 MiB of text, 89 MiB of gzip): 0.5 s and 577 MiB as one gzip member (348 MiB when the header line is a member of its own), 0.06 s and 94 MiB in 1 MiB members (quiet-host times; 0.8 s and 0.1 s on a busy host), where 0.1.3 took 0.00 s and 15 MiB, because it appended without reading. Memory grows with the file: about 6.5 times the compressed size for a one-member file. A plain (uncompressed) loose file is not affected: its `delete` reads only up to the first keyed line, 0.00 s and 15 MiB as in 0.1.3. `pop` and `popitem` already read the whole file in 0.1.3. Why it reads: the delete must know the file's column count, as TSVZ.py decides (at one column a key alone is a row, so the delete rewrites the file; your 2026-11-14 pick "Fix both in 0.1.4 (Recommended)"); a look at the first lines alone, by a decoder of its own, misjudged damaged files in the third review (a refused delete; a `popitem` loop that never ended), so it was removed. My reading of the gate: this is a new cost in time and memory on one rare shape (a compressed loose file), not a wrong result or lost data, and it comes with the fix you asked for, so 0.1.4 is "more tolerable" overall and I would not hold it; but it is slower than 0.1.3 on that shape, which a strict reading of "does not make an existing issue worse" would count. Options: **(a) release 0.1.4 with this cost, written as a 0.1.5 deferral (recommended):** 0.1.5's first part, a part reader that decodes one member at a time, lets the delete stop at the first keyed line as a plain file's does; / (b) hold 0.1.4 until that part reader is built and reviewed (a design of its own; everything else in 0.1.4 waits with it). Going back to 0.1.3's blind append is not offered: 0.1.4 reads a key alone as a row at one column (your pick), so a blind append there would delete nothing. Waits on it: 0.1.4's publish, tag and GitHub release; the scrub-look fix and its re-review go on meanwhile. Your words it touches: none dropped.
