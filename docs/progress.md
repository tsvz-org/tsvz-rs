## Questions waiting for the user
- **Decided 2026-11-16, chief's decision C77 (not the user's words; the user may reverse it; 0.1.4 shipped with it on 2026-11-17): Q10 option (a)**, release 0.1.4 with the slower `delete` in compressed loose files, written as a 0.1.5 deferral (the part reader), with the cost and its numbers in 0.1.4's release notes. Chief's reasons: the user's gate words ("if it makes the result more tolerable, we shall not gate it") and deferral words; time and memory on one rare shape, no wrong result or lost data, and it comes with the fix the user picked. The question as asked: **Q10. Release 0.1.4 with a slower `delete` in compressed loose files?** (Written 2026-11-16 on chief's order, with the cost in view; chief told you it was coming.) The cost: `tsvz delete` (and `pop`, `popitem`) in a compressed loose file (`.tsv.gz` and the like) now reads the whole file into memory before it writes. On 4,000,000 rows (228 MiB of text, 89 MiB of gzip): 0.5 s and 577 MiB as one gzip member (348 MiB when the header line is a member of its own), 0.06 s and 94 MiB in 1 MiB members (quiet-host times; 0.8 s and 0.1 s on a busy host), where 0.1.3 took 0.00 s and 15 MiB, because it appended without reading. Memory grows with the file: about 6.5 times the compressed size for a one-member file. A plain (uncompressed) loose file is not affected: its `delete` reads only up to the first keyed line, 0.00 s and 15 MiB as in 0.1.3. `pop` and `popitem` already read the whole file in 0.1.3. Why it reads: the delete must know the file's column count, as TSVZ.py decides (at one column a key alone is a row, so the delete rewrites the file; your 2026-11-14 pick "Fix both in 0.1.4 (Recommended)"); a look at the first lines alone, by a decoder of its own, misjudged damaged files in the third review (a refused delete; a `popitem` loop that never ended), so it was removed. My reading of the gate: this is a new cost in time and memory on one rare shape (a compressed loose file), not a wrong result or lost data, and it comes with the fix you asked for, so 0.1.4 is "more tolerable" overall and I would not hold it; but it is slower than 0.1.3 on that shape, which a strict reading of "does not make an existing issue worse" would count. Options: **(a) release 0.1.4 with this cost, written as a 0.1.5 deferral (recommended):** 0.1.5's first part, a part reader that decodes one member at a time, lets the delete stop at the first keyed line as a plain file's does; / (b) hold 0.1.4 until that part reader is built and reviewed (a design of its own; everything else in 0.1.4 waits with it). Going back to 0.1.3's blind append is not offered: 0.1.4 reads a key alone as a row at one column (your pick), so a blind append there would delete nothing. Waits on it: 0.1.4's publish, tag and GitHub release; the scrub-look fix and its re-review go on meanwhile. Your words it touches: none dropped.
