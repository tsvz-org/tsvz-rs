On 4,000,000 rows (228 MiB of text, 89 MiB of gzip): 0.5 s and 577 MiB as one gzip member (348 MiB when the header line is a member of its own), 0.06 s and 94 MiB in 1 MiB members (quiet-host times; 0.8 s and 0.1 s on a busy host), where 0.1.3 took 0.00 s and 15 MiB, because it appended without reading. - **Q5 is back with a question (2026-11-17, the user's words, relayed by chief): "on my machine it might be 3 microsends, how about on a sleeping harddrive? or a network file system?"** To measure before it is asked again: the extra listings' cost per request against the trust as built, on (1) a store on a spun-down hard disk (does a listing, or today's change-time check, wake the disk, or is it served from the kernel's cache?) and (2) a store on NFS, and SMB if one is to hand (round trips each way, with the mount's default attribute caching); then the numbers go into this question, with whether the recommendation changes. Until then the trust stays as built. Measured 2026-11-17 (scratchpad notes m014q5; tsvz-rs 0.1.4 code as built against the same with every check listing, in VM 901; no host disk was spun down, as they hold the user's data). The answers:
  - **Network file systems: no difference.** The trust is used only on local kernel file systems (ext4, XFS, btrfs, ZFS, f2fs, tmpfs); on NFS, SMB and FUSE the code as built already lists at every check. Counted on the wire with default mounts: a set/get pair is 11 RPCs on NFSv4.2, 10 on NFSv3 and 17 requests on SMB in both builds, at 0 to 70 s between requests; with 1 and 5 ms of added delay the times differ only by noise.
  - **A sleeping hard disk: a read-only `get` can wake it in always-list and not in the trust.** With warm caches neither reads the disk. After the kernel dropped the directory from its cache (an emptied cache, or 10 and 60 minutes idle under memory pressure), the first `get` read one 4 KiB block (the directory's own data) in always-list and none in the trust, every time (30 of 30; 4 of 4 idle cells). A `set` reads 3 to 4 blocks in both, so a write wakes the disk either way.
  - **A store in a directory with many other files: always-list costs grow with the directory.** Per set/get pair on local ext4: 100 other files +78 us (120 against 200 us), 1,000 +533 us (242 against 770 us), 10,000 +4.7 ms (1.5 against 6.3 ms); the first `get` after an emptied cache reads 1, 13 and 120 blocks.
  - **A quiet directory of a few files:** +16 syscalls per pair, +21 to +35 us on 80 to 105 us pairs in the VM (the 3 us on 9 us you saw, on a slower machine).
  - **My recommendation changes: keep the trust.** It costs the code and tests named below, but on a local disk it is what keeps a store in a large directory fast (three to four times) and a read from waking a sleeping disk; on a network mount there is nothing to drop. Options now: **Keep the trust (recommended)** / Always list.
